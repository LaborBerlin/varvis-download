# Development

This page summarizes the local development workflow for `varvis-download`.

## Quick Commands

Use Make for streamlined workflows:

```bash
make help           # Show all available commands
make dev            # Setup: install dependencies, lint, and test
make ci             # Run all quality checks (lint, format, type-check, test)
```

## Testing

```bash
# Using Make
make test           # Run unit tests
make test-int       # Run live integration tests when credentials are available

# Using npm
npm test                     # Run unit tests
npm test -- --coverage       # Run unit tests with coverage report
npm run test:integration     # Run live integration tests
```

Live integration tests use the varvis® Playground target and depend on external service availability. Unit tests and
local CI checks do not require Playground credentials.

## Code Quality

```bash
# Using Make
make lint           # Check code quality
make lint-fix       # Auto-fix lint issues where possible
make format         # Format with Prettier
make type-check     # Verify types

# Using npm
npm run lint
npm run lint:fix
npm run format
npm run type-check
```

## Security Checks

```bash
make audit          # Check production dependencies
make audit-all      # Check all dependencies
make audit-fix      # Apply npm audit fixes where available
make security       # Run audit and security-focused lint checks
```

The project uses dependency vulnerability scanning, ESLint security rules, and secret-detection linting to reduce common
development risks.

## Pull Requests and Releases

Use `make pr` from a clean working tree to prepare either a conventional pull request or a release pull request. The
script pushes the current branch and opens a draft pull request. For a release pull request, it also:

1. Updates `package.json` and `package-lock.json` to the selected version.
2. Generates the new `CHANGELOG.md` section with `git-cliff`.
3. Creates and commits a `release/v<version>` branch.

Run the complete local gate before starting and inspect the generated version and changelog before merging:

```bash
npm run check
make pr
```

Changelog entries are derived from conventional commit prefixes such as `feat:`, `fix:`, `docs:`, and `chore:`. Do not
add a release heading manually; review the section generated by `make pr` and correct commit messages or the git-cliff
configuration when an entry is missing or misclassified.

After the release pull request has passed review and CI, merge it and create the version tag from the updated `main`
branch:

```bash
git switch main
git pull --ff-only origin main
make release
```

`make release` creates a release on github using the `gh`cli. First a new tag is created and pushed, subsequently
the release gets created, including the current changelog as body and the source code archives as assets.

## Contributing

Before opening or merging changes:

1. Run `npm run check`.
2. Add or update tests for behavior changes.
3. Update documentation for new user-facing behavior.
4. Keep generated documentation in sync when API comments change.
